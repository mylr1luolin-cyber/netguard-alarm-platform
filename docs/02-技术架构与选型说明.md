## 3. 关键设计决策

### 3.1 为什么用 ThreadPoolTaskScheduler 而不是 `@Scheduled`

`@Scheduled(fixedRate)` 的间隔在启动时固定，无法在运行时调整。题目要求"告警规则可配置巡检间隔 5/10/30 分钟"，因此：

- `SchedulingConfig` 暴露 `ThreadPoolTaskScheduler inspectTaskScheduler`（poolSize=2，`removeOnCancelPolicy=true`）；
- `DynamicInspectScheduler` 持有 `ScheduledFuture`，启动时按规则排程，监听 `RuleChangedEvent` 后 `cancel(false)` 并按新间隔重排；
- `AtomicBoolean running` 防重入，避免一次巡检未结束时叠加执行。

### 3.2 为什么用 RabbitMQ 而不是直接调用通知

告警产生属于**核心链路**（必须落库），而通知属于**可失败链路**（邮件服务器可能超时）。用 MQ 解耦后：

- 告警落库不受通知失败影响；
- 通知重试、削峰由消费者承担；
- 队列配置死信交换机（`netguard.alarm.dlx` → `netguard.alarm.dlq`），消费异常的消息可追踪。

同时提供 `app.mq.enabled=false` 的降级实现 `LocalAlarmEventPublisher`（进程内直接调用 `NotifyService`），保证没有 RabbitMQ 的环境也能演示完整流程。

### 3.3 缓存与降级

`CacheService` 同时维护两个通道：

- Redis 通道：`StringRedisTemplate`，键 `netguard:device:status`（Hash：deviceId → `{status,deviceName,checkTime}` JSON）、`netguard:dashboard:summary`（30 秒 TTL）；
- 内存通道：`ConcurrentHashMap` + `ConcurrentHashMap<String, Map<String,String>>`。

`cacheMode=redis` 时启动 `ping` 探测，失败即置 `redisAvailable=false` 并全部走内存；之后每 60 秒重试一次恢复。这样单机演示不需要安装 Redis，生产环境开启 Redis 后自动生效。

### 3.4 连续失败阈值

单次探测失败不代表离线（网络抖动、设备瞬时繁忙）。`device.offline_count` 记录连续失败次数，只有 `offline_count == failThreshold` 时才创建告警（用 `==` 而非 `>=`，保证一次故障只告警一次）；探测成功后清零。告警恢复依赖"探测成功 + 设备此前为 OFFLINE"。

### 3.5 统一响应与异常

- 页面请求：`GlobalExceptionHandler` 渲染 `error/403`、`error/500` 并携带友好 `message`；
- AJAX 请求（`/api/**` 或 `X-Requested-With: XMLHttpRequest`）：返回 `Result.fail(...)` JSON；
- 业务校验失败抛 `BusinessException(code, message)`，由处理器统一转成闪存消息或 JSON。

## 5. 数据流示例（设备离线告警）

```
DynamicInspectScheduler.safeInspect()
  → InspectService.runInspect(AUTO, "system")
      → 逐设备 ProbeUtils.probe(ip, port, timeout)
      → DeviceService.applyProbeResult(device, online, now)
      → triggerAlarmIfNeeded(...)
          → AlarmService.createOfflineAlarm(device, typeName, rule)
              → alarm_record INSERT（PENDING）
              → AlarmEventPublisher.publish(AlarmMessage)
                  → RabbitMQ（app.mq.enabled=true）
                      → AlarmNotifyListener → NotifyService.notifyAlarm
                  → 或 LocalAlarmEventPublisher → NotifyService.notifyAlarm（降级）
                      → notify_record INSERT（PAGE/MAIL）
                      → MailService.sendHtml(...)（异步线程池 notifyExecutor）
                      → alarm_record.notify_sent = 1
      → inspect_detail 批量 INSERT + inspect_log INSERT
      → CacheService 清理看板缓存、刷新设备状态缓存
```

## 6. 多环境配置策略

| 环境 | 文件 | 数据库 | Redis | MQ | 邮件 |
| --- | --- | --- | --- | --- | --- |
| 开发 | `application-dev.yml` | 127.0.0.1:3306/netguard | 本机 6379（失败降级内存） | **关闭**（本地同步通知） | **关闭**（跳过发送） |
| 测试 | `application-test.yml` | 127.0.0.1:3307/netguard_test | db1 | 开启 | 关闭 |
| 生产 | `application-prod.yml` | 环境变量注入 | 环境变量 | 开启 | 开启（SMTP 环境变量） |

启动方式：`java -jar netguard.jar --spring.profiles.active=dev`（默认 dev）。

## 7. 已知限制与后续演进

1. 探测为串行遍历（单批 200 台内可接受），后续可改为 `CompletableFuture` 并发探测并限流；
2. 未接入 SNMP，无法采集 CPU/内存/端口流量等指标；
3. 邮件模板为内联 HTML，后续可迁移到 Thymeleaf 模板文件；
4. 多实例部署时定时任务会重复执行，需要引入分布式锁（Redis `SETNX`）或调度中心；
5. 通知渠道仅页面与邮件，`NotifyChannelEnum` 预留短信/企业微信扩展点。
